# Спецификация реализации проекта

## Назначение документа

Этот документ дополняет [`TASK.md`](./TASK.md) и фиксирует принятые инженерные решения для реализации тестового задания. Функциональные требования из исходного задания здесь не дублируются.

Если этот документ расходится с `TASK.md`, приоритет имеет `TASK.md`. Более строгие внутренние требования из этого документа применяются, если они не противоречат исходному заданию.

## Платформа и язык интерфейса

- `minSdk = 28`;
- `compileSdk = 37`;
- `targetSdk = 37`.

Поддерживаемые языки UI — русский (`ru`) и английский (`en`). Все пользовательские строки хранятся в Android string resources. Оба языка объявляются в `android:localeConfig`; на Android 13+ пользователь переключает язык через системную настройку языка приложения. На Android 12 и ниже UI следует языку системы с fallback на английский. Собственный переключатель языка внутри приложения не создаётся.

## Модульная структура

Базовая структура проекта:

```text
:app
:core:model
:core:network
:core:ui
:core:logging
:feature:cities
:feature:map
```

Общие настройки Gradle выносятся в convention plugins внутри `build-logic`, чтобы Android, Kotlin, Compose и test-конфигурация не копировались между модулями. Версии библиотек хранятся в `gradle/libs.versions.toml`; dynamic versions не используются.

Новый `core`-модуль создаётся только тогда, когда у него есть самостоятельная ответственность, несколько потребителей и понятный публичный API. Модули не должны появляться только ради формального разделения файлов.

### `:app`

Composition root приложения:

- `Application` и `MainActivity`;
- запуск и сборка графа Koin;
- корневой `NavHost`;
- подключение feature-модулей;
- конфигурация build types и application-level поведения.

### `:core:model`

Содержит общие модели, которые действительно используются несколькими фичами. В частности, общая модель города может использоваться списком, экраном информации и картой.

Модуль не должен превращаться в хранилище всех data class проекта. Feature-specific UI-модели и DTO остаются внутри соответствующих фич.

### `:core:network`

Содержит общую инфраструктуру Ktor:

- создание и конфигурацию единственного `HttpClient`;
- HTTP engine;
- JSON content negotiation;
- таймауты;
- общую обработку HTTP-ответов и сетевых исключений;
- debug-only HTTP logging;
- конфигурацию base URL.

Модуль не содержит API конкретной фичи. `CitiesApi`, `MapApi` и их DTO принадлежат соответствующим feature-модулям.

### `:core:ui`

Содержит общую Compose-инфраструктуру:

- `MaterialTheme`, цветовую схему и типографику;
- семантические design tokens для spacing, размеров и форм, взятые из Figma;
- общие компоненты, реально используемые несколькими экранами;
- общие loading, empty и error primitives;
- общие иконки и визуальные ресурсы.

Feature-specific размеры и компоненты не выносятся в `core:ui` заранее. В коде не должно быть бессистемно разбросанных цветов и повторяющихся magic numbers, но это не означает, что каждый `dp` обязан быть глобальным токеном.

### `:core:logging`

Содержит единую точку входа для журналирования и её Android-реализацию. В качестве backend используется Timber.

Требования:

- отсутствие прямых вызовов `android.util.Log` в feature-коде;
- подробное журналирование доступно в debug-сборке;
- release-сборка не пишет чувствительные данные, query-параметры и тела ответов;
- сетевое логирование согласовано с общей политикой логирования.

### Feature-модули

Каждый feature-модуль является вертикальным срезом и внутри разделяется пакетами, а не дополнительными Gradle-модулями:

```text
feature/<name>/
  data/
    api/
    dto/
    repository/
  domain/
    model/
    repository/
    usecase/       # только при наличии отдельной бизнес-операции
  presentation/
    contract/
    model/
    screen/
    component/
```

Use case не создаётся для простого проксирования одного вызова repository. Он появляется только при наличии отдельной переиспользуемой бизнес-операции или координации нескольких источников данных.

`feature:cities` включает список городов и информацию о выбранном городе. `feature:map` включает загрузку городов в видимой области карты, маркеры и модальное окно выбранного города.

Зависимости feature-модулей друг от друга запрещены. Общие модели и UI-компоненты выносятся в подходящий `core`-модуль.

## Архитектура feature-модуля

Направление зависимостей внутри фичи:

```text
presentation -> domain <- data
```

- UI работает с UI-моделями и контрактом ViewModel.
- Domain не зависит от Compose, Android UI, Ktor и Koin.
- Data-слой реализует domain-интерфейсы repository.
- DTO не передаются в presentation.
- Преобразования DTO → domain и domain → UI выполняются явно.
- Исключения библиотек не должны становиться частью UI-контракта.

Допускается не создавать отдельную domain-модель, если объект не пересекает архитектурную границу и дополнительное преобразование не даёт пользы. Для `City` отдельная общая модель оправдана, поскольку она используется несколькими экранами и фичами.

## Orbit MVI

Orbit используется в соответствии с официальными рекомендациями библиотеки:

- ViewModel реализует `ContainerHost<State, SideEffect>`;
- единственным источником состояния экрана является Orbit container;
- изменение состояния выполняется внутри Orbit intent через `reduce`;
- одноразовые события публикуются через `postSideEffect`;
- UI подписывается на state и side effects с учётом lifecycle;
- asynchronous work не запускается напрямую из stateless composable;
- тесты контейнеров пишутся с `orbit-test`.

Для каждого экрана определяется собственный контракт:

- immutable `State` содержит всё необходимое для отрисовки;
- `SideEffect` содержит только одноразовые действия: навигацию, открытие браузера и подобные внешние эффекты;
- публичные intent-функции ViewModel отражают пользовательские действия;
- длительные ошибки, retry и loading являются частью `State`, а не side effect.

UI разделяется на два уровня:

```text
FeatureRoute
  получает ViewModel из Koin
  собирает Orbit state и side effects
  выполняет навигационные эффекты

FeatureScreen
  stateless
  принимает State и callbacks
  используется в Preview и Compose UI-тестах
```

Данные, необходимые после process recreation, сохраняются через `SavedStateHandle`. Не следует сохранять большие списки или сетевые DTO в `Bundle`.

## Поиск и собственная пагинация

Paging 3 не используется. Пагинация реализуется как явная state machine внутри Orbit ViewModel. Это позволяет показать управление состоянием, конкуренцией запросов и ошибками без скрытой логики стороннего paging-фреймворка.

Состояние списка должно разделять состояние основного контента и состояние пагинации. Недопустимы наборы независимых boolean-флагов, допускающие противоречивые комбинации.

Пример концептуальной модели:

```kotlin
sealed interface ContentState {
    data object Initial : ContentState
    data object Loading : ContentState
    data class Content(val cities: List<CityUi>) : ContentState
    data class Empty(val query: String) : ContentState
    data class Error(val error: ErrorUi) : ContentState
}

sealed interface PaginationState {
    data object Idle : PaginationState
    data object Loading : PaginationState
    data object EndReached : PaginationState
    data class Error(val error: ErrorUi) : PaginationState
}
```

Конкретная форма Kotlin-контракта может отличаться, но должна сохранять невозможность невалидных состояний.

### Правила поиска

- значение поля обновляется в UI немедленно;
- поисковый запрос выполняется через `300 ms` после последнего изменения текста; значение хранится в одной централизованной константе;
- initial load при открытии экрана выполняется сразу и не ожидает debounce;
- одинаковые последовательные запросы не повторяются;
- новый query отменяет предыдущую загрузку;
- ответ устаревшего запроса не может изменить актуальное состояние;
- смена query сбрасывает страницу, накопленные элементы и pagination state;
- перед сетевым запросом query очищается от пробелов по краям;
- пустой query означает полный список городов с обычной пагинацией; параметр `query` в таком запросе не передаётся;
- переход между непустым и пустым query считается сменой запроса, отменяет активную загрузку и начинает полный список с первой страницы.

### Правила пагинации

- начальная страница — `1`, размер страницы — `20`; оба значения задаются централизованно;
- запрос следующей страницы выполняется при приближении к концу списка;
- одновременно разрешён только один pagination request;
- повторные события от `LazyListState` не создают дублирующие запросы;
- элементы объединяются по стабильному идентификатору без дубликатов;
- API списка фактически возвращает объект `{ items, limit, page, total }`; отдельного поля `hasMore` нет, а `total` содержит число элементов с учётом текущего query;
- основной критерий конца списка вычисляется по значениям ответа: `page * limit >= total`;
- защитный критерий конца — пустая страница; если `total` отсутствует или некорректен, используется fallback `items.size < limit`, чтобы клиент не создавал бесконечные запросы;
- для вычисления конца используются возвращённые API `page` и `limit`, а не только запрошенные клиентом значения;
- ошибка следующей страницы сохраняет ранее загруженный список;
- pagination error отображается в конце списка и имеет отдельный retry;
- initial retry и pagination retry повторяют соответствующую операцию;
- смена поискового запроса отменяет активную пагинацию.

Контракт списка проверен прямыми запросами 4 сентября 2026 года. Отсутствующий и пустой `query` возвращают одинаковый полный набор (`total = 177738` на момент проверки). API использует 1-based страницы: для `limit = 20` страница `8887` содержит 18 элементов, а страница `8888` пуста. Значения `limit` от `1` до `100` принимаются API; приложение намеренно использует `20`, чтобы первая отрисовка и последующие порции оставались небольшими и предсказуемыми.

## UI-состояния

Для списка обязательны:

- initial skeleton;
- успешный контент;
- пустой результат с отдельным placeholder;
- ошибка initial load с полноэкранным retry;
- загрузка следующей страницы внизу списка;
- ошибка следующей страницы с сохранением контента и inline retry;
- состояние достижения конца списка.

Для карты обязательны:

- загрузка данных для видимой области;
- успешное отображение маркеров;
- отсутствие городов в области;
- ошибка загрузки с retry без разрушения самой карты;
- выбранный маркер и модальное окно с информацией;
- корректная обработка повторного выбора и закрытия модального окна.

Общие требования к UI:

- визуальные значения берутся из темы и design tokens;
- UI-модели уже содержат подготовленный для отображения текст;
- форматирование населения и страны не выполняется внутри composable;
- экраны имеют Preview для основных состояний;
- ошибки имеют понятное пользователю сообщение и доступное действие восстановления;
- системные inset, клавиатура и back navigation обрабатываются корректно;
- светлая тема обязательна; тёмная тема реализуется только при наличии времени и полного набора токенов.

### Код страны и локаль отображения

Контракт `country` проверен 4 сентября 2026 года прямыми запросами к обоим API. В ответах поле содержит двухсимвольный код в верхнем регистре: например, `CN`, `RU`, `US`, `GB`. Для стандартных стран эти значения соответствуют ISO 3166-1 alpha-2. При этом API также фактически возвращает `XK` для городов Косово (например, для `Pristina`) — это пользовательский код, а не официально присвоенный ISO 3166-1 alpha-2. Поэтому приложение рассматривает `country` как непрозрачный двухбуквенный код и не отклоняет значение только из-за его отсутствия в стандартном списке ISO.

Макет показывает полные названия стран. Их преобразование выполняется отдельным formatter-компонентом в активной app locale, выбранной для приложения: `Китай`/`China`, `Россия`/`Russia`. Для `XK` formatter должен вернуть `Косово` в `ru` и `Kosovo` в `en`, даже если версия Android не умеет локализовать этот код. Для неизвестного или неподдерживаемого значения используется исходный код без потери данных. Форматирование не выполняется внутри composable.

## Карта

Карта является обязательной частью принятого scope, несмотря на обозначение дополнительного задания в исходном документе.

Используется MapLibre Native Android `13.4.1` с OpenGL renderer и подложкой OpenFreeMap Liberty (`https://tiles.openfreemap.org/styles/liberty`). Решение не требует регистрации и API-ключа. Атрибуция OpenStreetMap/OpenMapTiles остаётся видимой; отсутствие SLA у OpenFreeMap принимается как ограничение тестового проекта.

MapLibre выбран для тестового задания из-за платного доступа к 2ГИС; для реального production-проекта предпочтительным выбором был бы 2ГИС Mobile SDK.

`MapView` встраивается в Compose через `AndroidView` с передачей lifecycle-событий. Города отображаются одним `GeoJsonSource` и `SymbolLayer`; нажатие определяется через `queryRenderedFeatures()` и открывает Compose modal bottom sheet.

Запрос данных карты не должен отправляться на каждое промежуточное движение камеры:

- изменения viewport агрегируются;
- запрос выполняется после завершения движения камеры и debounce;
- одинаковые параметры не запрашиваются повторно;
- новый viewport отменяет устаревший запрос;
- `centerLat` и `centerLng` соответствуют центру экрана, а `radius` — максимальному расстоянию до углов фактической видимой области;
- результат устаревшего запроса не может перезаписать актуальные маркеры.

Транзитивные `ACCESS_COARSE_LOCATION` и `ACCESS_FINE_LOCATION` удаляются через manifest merger, поскольку геолокация пользователя не входит в scope. Для карты нужны только сетевые разрешения.

## Networking

Для REST используется Ktor Client без Retrofit.

Базовая конфигурация:

- подходящий Android HTTP engine;
- `ContentNegotiation` с `kotlinx.serialization`;
- `ignoreUnknownKeys = true`;
- connect, request и socket timeouts;
- `expectSuccess` или эквивалентная централизованная проверка статусов;
- типизированное преобразование network, HTTP и serialization errors;
- HTTP logging только в debug-сборке.

API использует cleartext HTTP. Он разрешается только для указанного API-домена через Network Security Config. Глобальное разрешение cleartext-трафика не используется.

## Dependency Injection

Используется Koin.

- зависимости передаются через конструкторы;
- каждый Gradle-модуль публикует собственный Koin module;
- `:app` собирает итоговый dependency graph;
- `HttpClient` и repositories имеют корректный singleton lifecycle;
- ViewModel создаются через Koin ViewModel DSL;
- feature-код не использует service locator;
- stateless composable не получает repository или API через Koin;
- DI-конфигурация допускает замену реализаций fake-объектами в тестах.

## Навигация

Используется AndroidX Navigation Compose с type-safe routes на основе Kotlin Serialization.

- feature-модуль предоставляет destination/graph builder API;
- `NavController` не передаётся в stateless screen;
- ViewModel публикует navigation side effect, а `Route` выполняет переход;
- аргументы маршрутов минимальны и пригодны для восстановления процесса;
- для экрана информации передаются только необходимые значения выбранного города;
- открытие внешнего браузера выполняется через отдельный side effect;
- поисковый URL строится с корректным URL encoding;
- отсутствие приложения, способного обработать intent, не приводит к crash.

## Тестовая стратегия

Тесты разделяются на unit, integration и UI. Реальные сетевые запросы не являются частью детерминированного CI.

Тесты добавляются или обновляются при изменении логики и значимых контрактов, с учётом существующего покрытия. Для каждой задачи не требуется отдельный новый тест: изменения только в документации или изменения без затронутого поведения не требуют формальных unit-тестов. Уже покрытое поведение не нужно дублировать ради количества тестов.

Тест должен проверять самостоятельный ожидаемый результат: переход состояния, вычисление, обработку ошибки или взаимодействие компонентов. Проверки вида «константа равна литералу», прямых присваиваний и копии алгоритма реализации не добавляются. Если значение влияет на требования, проверяется его эффект: например, debounce задерживает запрос и объединяет ввод, а не просто `SEARCH_DEBOUNCE_MS == 300`. Проверки фактического HTTP-запроса, сериализации и других внешних контрактов остаются полезными, даже если ожидаемый результат содержит фиксированные значения.

### Unit-тесты

Обязательные сценарии по мере реализации соответствующей логики (общий набор покрытия проекта, а не требование добавлять тесты в каждой задаче):

- initial load: loading → content;
- initial load: loading → error;
- retry после initial error;
- debounce поискового запроса;
- отмена устаревшего поиска;
- сброс списка и страницы при изменении query;
- empty search result;
- успешная загрузка следующей страницы;
- защита от параллельных pagination requests;
- удаление дубликатов;
- определение конца списка;
- pagination error с сохранением текущего контента;
- retry конкретной страницы;
- отмена пагинации при новом поиске;
- корректные side effects навигации и открытия браузера;
- форматирование населения и страны, включая fallback.

Используются fake repositories, `kotlinx-coroutines-test` и `orbit-test`. Тесты времени работают с virtual time и не используют реальные задержки.

### Integration-тесты

На JVM с Ktor `MockEngine` проверяется связка API и repository:

- правильный HTTP method, path и query-параметры;
- десериализация репрезентативного JSON;
- mapping DTO → domain;
- обработка пустого ответа;
- обработка HTTP error;
- обработка malformed JSON;
- преобразование transport exception в domain error.

Отдельно проверяется DI smoke test: основные Koin-модули должны собираться без отсутствующих и циклических зависимостей.

### Compose UI-тесты

Минимальный набор:

- список отображает полученные города;
- ввод поискового текста вызывает ожидаемое UI-событие;
- empty state отображается корректно;
- initial error содержит retry;
- pagination error отображается вместе с существующим списком;
- нажатие на город инициирует переход;
- выбор маркера открывает модальное окно карты.

Screenshot-тесты не являются обязательными на первом этапе. Их можно добавить для ключевых экранов после стабилизации UI.

## Git и выпуск

- Коммиты должны быть небольшими, логически завершёнными и иметь содержательные сообщения.
- В истории не должно быть `final`, `fix`, `changes` и других сообщений без контекста.
- Перед сдачей создаётся версия в формате Semantic Versioning: `MAJOR.MINOR.PATCH`.
- Первый завершённый выпуск получает тег `v1.0.0`.
- Для тега создаётся GitHub Release с release notes и устанавливаемым APK.
- Секреты, API-ключи, signing credentials, `local.properties`, IDE state и локальные артефакты не коммитятся.

## Критерии готовности

Проект считается готовым к сдаче, когда:

- реализован весь обязательный функционал из `TASK.md`;
- реализована карта с модальным окном;
- все описанные UI-состояния доступны и корректно восстанавливаются через retry;
- поиск, пагинационная state machine списка и обновление карты по viewport покрыты тестами;
- unit- и integration-тесты проходят локально;
- Compose UI-тесты основных сценариев проходят локально;
- сборка, Android Lint, ktlint и Detekt проходят без ошибок;
- README соответствует фактической реализации;
- проверена release-сборка;
- создан тег `v1.0.0` и GitHub Release с APK;
- репозиторий не содержит секретов и локального мусора.
